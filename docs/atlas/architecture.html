01 · process topology

Five processes the shell spawns and supervises

The Electron main process is the conductor. On boot its daemon-managers spawn the Core broker, the voice stack, the mesh nodes, and the scene server — each a separate process on its own loopback port. Nothing binds beyond 127.0.0.1 except the scene server, which adds Tailscale for the headset.

shell mesh edge (signed) voice / raven-core scene server (HTTP + WS) Python process TypeScript/Node process
shell/electron/main/index.ts (boot) · services/{coreManager,ravenDaemonManager,sceneServerDaemonManager,nodeManager}.ts · daemons/README.md · core/README.md

The Python brain never touches the mesh directly through a privileged channel — it registers as the raven node and reaches every capability through mesh.invoke(), the same signed path the shell uses. Voice and shell are peers on the fabric, not a layered hierarchy.

02 · the mesh — the spine

Authorization is graph membership, nothing else

manifest.yaml declares 19 nodes and 69 directed edges. An edge present means the call is permitted; absent means denied. There is no policy field, no role table, no back channel — to grant a capability you add a line. Identity is a per-node HMAC secret referenced as env:MESH_*_SECRET and injected by the shell at boot.

03 · the voice pipeline

Mic → Gemini Live → a tool → the mesh → spoken + a panel

The brain is Gemini 2.5 native-audio Live. It hears continuously, decides when to call a function, and the orchestrator routes that call. Most tools cross the mesh; a few are raven-local. Answers come back as speech; visual ones also POST a panel that surfaces in the cockpit.

  • Hear

    Audio streams in over PyAudio to raven-core's Gemini Live session. Typed CLI input rides the same brain — one model for spoken and typed.

  • Decide

    Gemini emits a function_call. The orchestrator's handle_function_call_async dispatches by name across the discovered tool modules.

  • Invoke

    For mesh tools, the handler calls mesh.invoke('node.surface') → a signed envelope to Core :8000 → the edge graph permits → the node runs and returns. Raven-local tools (memory, navigate, draft_lane) skip the mesh.

  • Speak

    The result is fed back into Gemini, which narrates one line. Side-effect tools (notify, report_gap, draft_lane) return a tiny ack, never content to read aloud.

  • Show

    visualize routes through the visualizer node, which POSTs a panel to the scene server. The shell's WS subscriber pushes it to the renderer and it lands in the Scene view.

04 · the data layer

Everything durable lives under one userData root

No central database. Each node namespaces its own store under $userData/data/<node>/; the mesh runtime (pids, logs, the signed-envelope audit) sits under $userData/mesh/; the voice daemon and a little renderer UI state sit at the top. The shell hands each spawned node a writable root as AETHER_DATA_DIR.

$userData/ # Electron app.getPath('userData') ├── mesh/ # mesh runtime — meshRuntimeDir() │ ├── core.pid · core.log │ ├── audit.log # every signed envelope, append-only │ └── <node>.pid · <node>.log # per-node runtime ├── data/ # durable node state — nodeDataDir() │ ├── intents/gaps.jsonl # the gap ledger · append-only + fsync │ ├── macos_mail/mail.db # SQLite (WAL) │ ├── news_feeds/news.db │ ├── finance/history.db # + in-memory quote cache │ ├── clipboard_history/clipboard.db │ ├── macos_messages/messages.db # mirror of ~/Library/Messages/chat.db (read-only) │ ├── architect/drafts/<slug>-<ts>.md # lane drafts · raven-local, no mesh hop │ └── raven-avp/scene_state.json # scene-server persisted SceneDoc ├── raven/ # raven-daemon dir │ ├── daemon.pid │ └── transcripts/session-<ts>-<id>.jsonl # survive restart └── scene-order.json # user's drag-reordered panel sequence

Two stores carry the system's self-knowledge: gaps.jsonl — the append-only log of what Aether was asked and could not do, the input to the self-building loop — and the transcripts/ JSONL, what it heard and said, surfaced in the Chats view. The audit.log is the third: a complete record of every signed mesh hop.

06 · the self-building loop

aether-rag — a retrieval brain, now served over MCP

The standalone RAG core under daemons/aether-rag/ indexes Aether's own corpus (governance log, DECISIONS, CHANGELOG, CLAUDE.md, scene protocol, release notes, READMEs, manifest) with fastembed (bge-small-en-v1.5, ONNX, no torch) + sqlite-vec; index at .rag/index.db. As of #187 it is wrapped as a stdio MCP server (server.py) exposing one read-only tool — search_corpus(query, k, source_filter) — registered project-scoped in a committed .mcp.json. This is Aether's first real adoption of MCP: an MCP server can serve both the voice brain and the spawned implementers, which a mesh node cannot. Client one is live — every Claude Code session in the repo inherits the corpus, and CLAUDE.md §13.13 Precedent-First Implementers now makes a search_corpus query the default discovery step before each build (this atlas's own drafts route through it).
